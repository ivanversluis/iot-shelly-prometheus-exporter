- (direction) Create an evidence-based production-readiness specification for the existing MVP; distinguish repository facts from recommendations, keep scope practical, produce independently implementable stories with acceptance criteria, and do not implement application changes.
- (note) Evidence snapshot inspected at commit 2a675889a572141407a58541dab26022d6d3f44f: AGENTS.md, README.md, docs/DESIGN.md, exporter source, tests, Makefile, Dockerfile, pyproject.toml, requirements.txt, GitHub Actions workflow, git history, and tags.
- (note) Baseline verification on local Python 3.14.7 passed 23 tests with 76 percent total coverage; CI and container target Python 3.12.
- (note) Credential exposure risk was reproduced with a fake marker: a requests HTTP exception string included the full prepared query URL; current generic exception logging can therefore disclose an auth query parameter.
- (note) Metric staleness was reproduced: a labelled device sample remained in the default registry after a subsequent successful empty-device update.
- (capability) CAP-1: Runtime configuration is rejected safely when required values, endpoint shape, numeric bounds, or log level are invalid; valid documented configuration starts normally.
- (capability) CAP-2: Poll failures are classified and reflected in exporter health without crashing, exceeding the Shelly rate limit, or retrying within a polling cycle.
- (capability) CAP-3: Diagnostics remain useful while all credential-bearing URLs, parameters, objects, payload fragments, and exception text are redacted.
- (capability) CAP-4: Published Prometheus identity remains compatible while successful scrapes retire samples that no longer exist and failed scrapes retain last known device data with explicit failure signals.
- (capability) CAP-5: Automated tests deterministically cover configuration, client errors, poll-loop state, metric lifecycle, and secret-safe logging without live network access or process-global collector collisions.
- (capability) CAP-6: The container build context and runtime exclude secrets and development artifacts, preserve the non-root runtime, expose metrics, and terminate cleanly.
- (capability) CAP-7: Pull requests and releases pass reproducible Python, quality, security, container, and version-consistency gates before publication.
- (capability) CAP-8: Maintainer and operator documentation accurately describes configuration, failures, metric lifecycle, safe local and container use, CI behavior, releases, and the boundary with the homelabs repository.
- (constraint) Preserve the published shelly metric names, label keys and meanings, unit suffixes, device identity from _dev_info.id, and shared Gen1 and Gen2 relay query surface unless an explicit migration is approved.
- (constraint) Keep device discovery and status collection to one GET request to device/all_status with show_info and no_shared per poll cycle; never add per-device fan-out or intra-cycle retries, and respect the account-wide one-request-per-second limit.
- (constraint) Never use real Shelly or Vault credentials in automated tests, fixtures, logs, examples, build contexts, or committed files.
- (constraint) Retain Python 3.12 compatibility and the container numeric non-root 1000:1000 no-home runtime.
- (constraint) Keep runtime dependency declarations synchronized because Make, CI, and Docker consume requirements.txt while project metadata also declares dependencies in pyproject.toml.
- (constraint) Deployment manifests, scrape configuration, dashboards, ExternalSecret, and NetworkPolicy remain owned by the separate homelabs repository.
- (decision) Recommend absolute HTTPS Shelly server URLs with a host and no embedded credentials, query, or fragment; positive request timeout, poll interval of at least one second, port range 1 through 65535, and recognized logging levels.
- (decision) Recommend no automatic retry inside a poll; schedule the next attempt after the configured interval, extended by a valid HTTP Retry-After value for rate-limit responses.
- (decision) Recommend sanitizing exceptions before logging and testing captured logs against fake secrets and auth-bearing URLs.
- (decision) Recommend retiring vanished device and field label children only after a successful complete response; failed polls keep prior samples and expose failure through shelly_up, error count, and last-success age.
- (decision) Recommend injectable collector registry and polling dependencies so tests isolate metric state and execute one poll iteration without sleeping or networking.
- (decision) Recommend a CI coverage floor of 85 percent for the small codebase, plus linting, dependency vulnerability checks, image build, and non-root metrics smoke testing.
- (decision) Recommend adding a Docker build-context exclusion file, retaining explicit COPY inputs, and verifying clean SIGTERM exit within ten seconds.
- (decision) Recommend semantic v-prefixed release tags that match the project metadata version, immutable version and commit image tags, latest only from the default branch, and human-readable release notes.
- (decision) Recommend correcting current documentation drift: pull requests build but do not push an image, and the rollout checklist contains stale exporter publication status.
- (assumption) Assume one exporter instance serves one Shelly account; high availability, shared caches, and distributed rate limiting are outside this milestone.
- (assumption) Assume an 85 percent coverage floor is proportionate after poll-loop and failure-path tests are added.
- (question) Which semantic version should identify the completed production-readiness milestone: the next 0.x release or 1.0.0?
- (question) Should required homelabs dashboard, alert, and deployment compatibility changes ship in the same delivery or be tracked as a coordinated sibling-repository follow-up?
